# Reflection

The most challenging part of this assignment was connecting the training and serving stages in a way that works consistently across local Docker execution and Kubernetes. The model itself is relatively straightforward, but an MLOps deployment requires the surrounding infrastructure to agree on paths, configuration, storage, ports, health checks, and image behavior. I addressed this by keeping training parameters in YAML, allowing the configuration path to be selected through an environment variable, and using a shared Kubernetes PersistentVolumeClaim so that the training Job can write the model checkpoint and the serving Deployment can mount the same checkpoint read-only.

Another important challenge was keeping the two Docker images purpose-specific. The training image contains only the packages needed to train the PyTorch model, while the serving image contains the inference API dependencies and runs the application as a non-root user. I also added a Docker HEALTHCHECK and Kubernetes liveness and readiness probes so that container and cluster health are observable rather than assumed.

The Git workflow reinforced the idea that MLOps includes software-engineering practices, not only model training. I used a develop branch, separate feature branches, Conventional Commit messages, Pull Requests, and GitHub Actions tests. This creates traceability for each change and makes it easier to review or reproduce the deployment.

Finally, Kubernetes introduced resource and lifecycle considerations that do not appear during local Python development. The training workload is represented as a finite Job with explicit CPU and memory requests/limits, while inference is represented as a replicated Deployment with rolling updates, a Service, and an HPA. The end-to-end validation demonstrated how the same trained artifact progresses from training to a scalable prediction endpoint. Overall, the assignment showed how source control, containerization, orchestration, persistent storage, configuration management, testing, and model serving work together as one production-style ML lifecycle.
